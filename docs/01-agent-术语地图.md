# Agent 开发术语地图（面试版）

> 用途：在你脑子里建一张坐标图。以后看代码、看文档、被面试官追问时，能立刻定位"这个概念属于哪一层、解决什么问题"。
> 每个词条格式：**是什么 → 为什么需要 → 关键细节（面试加分点） → 面试怎么问**

---

## 0. 先立坐标：Agent 和普通 Chatbot 的区别

| | Chatbot（聊天机器人） | Agent（智能体） |
|---|---|---|
| 能不能调工具 | 不能，只会说话 | 能调 API、查库、跑代码 |
| 有没有循环 | 一问一答，单轮 | 感知→推理→行动→观察，多轮自动循环直到任务完成 |
| 有没有状态 | 只有对话历史 | 有状态机（LangGraph 的 State），可持久化、可断点续跑 |
| 谁决定下一步 | 用户 | **模型自己决定**（调哪个工具、要不要再检索一次） |

一句话定义：**Agent = LLM（大脑）+ Tools（手脚）+ 循环控制（神经系统）+ Memory（记忆）**。

面试开场常问："你觉得 Agent 和普通大模型应用的区别是什么？"——答这张表就稳了。

## 1. 模型与提示层

### 1.1 Token 与上下文窗口
- **是什么**：Token 是模型处理文本的最小单位（中文大约 1 字≈1-2 token）。上下文窗口是一次请求能容纳的最大 token 数（输入+输出）。
- **为什么重要**：直接决定成本、延迟，以及**你能塞多少检索结果进 prompt**。这是 RAG 设计的硬约束。
- **细节**：不同模型计价不同；长上下文不等于都能用好（存在"中间遗忘"lost-in-the-middle 现象，重要信息放开头和结尾效果更好）。
- **面试**："你项目里一次请求大概多少 token？怎么控制成本？"

### 1.2 采样参数：temperature / top_p
- **temperature**：越低输出越确定（0 = 贪心，适合结构化、抽取任务）；越高越发散（适合创意）。
- **top_p**：核采样，从累计概率达到 p 的候选里采样。
- **工程经验**：RAG/Text2SQL 这类要准确的任务，temperature 设 0 或 0.1；不要同时调 temperature 和 top_p。

### 1.3 幻觉 Hallucination
- **是什么**：模型编造看似合理但错误的内容。
- **RAG 的核心价值之一就是抑制幻觉**：让答案有外部依据。但 RAG 不能完全消灭幻觉（检索到错误片段照样胡说）。
- **兜底手段**：引用溯源、让模型输出"未找到则明确拒答"、对答案做 faithfulness 校验。

### 1.4 Prompt Engineering
- **Zero-shot / Few-shot**：给不给示例。Few-shot 能稳定输出格式。
- **Chain-of-Thought（CoT）**：让模型"先想再答"，显著提升推理类任务准确率；代价是 token 变多。
- **角色消息**：System（设定身份与规则）/ User（用户输入）/ Assistant（模型回复）/ Tool（工具返回结果）四种角色。
- **2026 视角**：单独说"我会 prompt engineering"已经不够了，业界升级为 **Context Engineering（上下文工程）**——不只写提示词，而是管理整个上下文窗口里放什么、什么时候放、怎么压缩。

### 1.5 Function Calling（函数调用）
- **是什么**：模型原生能力。你向模型声明一批函数（名称+JSON Schema 描述+参数），模型不直接执行代码，而是**输出"我要调用哪个函数、参数是什么"的结构化结果**，由你的程序执行后再把结果回传。
- **关键点**：模型只输出"调用意图"，**执行在你这边**（这是安全边界，也是面试常考点）。
- **细节**：`tool_choice` 可强制/禁用调用；支持并行调用（一次返回多个函数调用）。

### 1.6 Tool Calling（工具调用）
- **和 Function Calling 的区别（必考辨析）**：
  - Function Calling = **模型层能力**（OpenAI/GLM 等模型提供的 API 特性）
  - Tool Calling = **框架层封装**（LangChain 的 `@tool` 装饰器、bind_tools 等，把函数注册给模型并自动完成"调用→回传→继续生成"的循环）
- 类比：FC 是发动机，Tool Calling 是整车。

### 1.7 结构化输出
- **是什么**：强制模型按指定 schema 输出（JSON / Pydantic 类）。
- **实现方式**：JSON Mode、Function Calling 反向利用、`response_format` + Pydantic 模型。
- **为什么重要**：Agent 要解析模型输出做下一步决策，格式不稳就崩。LangChain 有类型校验 + 重试机制。

### 1.8 流式输出 Streaming
- 逐 token 返回（`stream=True` / `.stream()`），前端打字机效果。
- **工程点**：Agent 场景下流式不只是"好看"，而是**降低感知延迟**；工具调用过程中的中间步骤也可以通过回调流式展示（提升可信度）。

## 2. RAG 层（W2 主线，最核心）

### 2.1 为什么需要 RAG
三个动机：**① 模型知识有时效性和盲区 ② 私有数据不能进训练集 ③ 需要可溯源的答案**。
对比方案：RAG vs 微调——RAG 解决"知识"问题，微调解决"行为/风格/格式"问题，**先 RAG 后微调**是常识顺序。

### 2.2 标准链路（六步）
```
加载 Load → 解析 Parse → 切分 Chunk → 向量化 Embed → 入库 Store
                                                      ↓
用户提问 → 检索 Retrieve（召回） → 重排 Rerank（精排） → 组装 Prompt → 生成 Generate
```
每一步都能单独优化，也能单独出题。

### 2.3 切分 Chunking
- **策略**：固定长度（简单）、递归字符切分（推荐默认，按段落/句子递归）、按文档结构（Markdown 标题层级）、**语义切分**（按 embedding 相似度合并，效果最好成本最高）。
- **参数**：`chunk_size`（太大→噪声多，太小→语义不完整）、`overlap`（防止切断语义）。
- **进阶：父子块 / small-to-big**：用小 chunk 做检索（精准），命中后返回它所属的大块（完整上下文）给模型。这是面试加分项。
- **面试**："你的 chunk 大小怎么定的？有没有做过对比实验？"（这就是我让你做评测集的原因）

### 2.4 Embedding 向量化
- 常用：bge-m3（中文强）、text-embedding-3、智谱 embedding 等。
- **细节**：维度（768/1024/1536）、是否归一化、**相似度度量**（余弦相似度 vs 内积 vs 欧氏距离，归一化后余弦=内积）。
- 注意：**检索用的 embedding 模型必须和入库时一致**。

### 2.5 向量数据库
- 选型：Milvus（分布式、生产级）、Qdrant（轻量好用）、pgvector（Postgres 扩展，已有 PG 就直接用）、Faiss（库而非服务）。
- **索引类型**：FLAT（暴力，100% 召回）、HNSW（图索引，快且召回率高，最常用）、IVF（聚类倒排）。
- **元数据过滤**：先按 metadata（如文档来源、权限、时间）过滤再向量检索，效率和准确度都更高。
- **面试**："为什么选 Milvus 不选 pgvector？"——答数据量级、是否需要分布式、团队已有基础设施。

### 2.6 检索策略（拉开差距的地方）
- **稠密检索 Dense**：向量语义匹配，懂同义词，怕精确关键词（如型号、人名）。
- **稀疏检索 Sparse（BM25）**：关键词匹配，怕同义改写。
- **混合检索 Hybrid**：两者都做，用 **RRF（倒数排名融合）** 合并结果。**这是现在的主流做法**。
- **MMR**：最大边际相关性，在相关性和多样性间权衡，去掉高度重复的片段。
- **查询改写**：用户问得太短/有歧义时，让 LLM 改写成更适合检索的 query（multi-query、HyDE 生成假设答案再检索）。
- **多跳检索 Multi-hop**：复杂问题拆成多个子问题，检索多次再汇总。

### 2.7 Rerank 重排
- **两阶段架构**：向量检索（快、召回多，取 top-50~100）→ Rerank 模型精排（慢、准，取 top-3~5）。
- **原理**：检索是双塔（query 和 doc 分别编码），Rerank 是 **cross-encoder**（query 和 doc 一起过模型，能捕捉交互，更准但更慢）。
- 常用：bge-reranker、Cohere Rerank。
- **面试**："加了 rerank 之后指标提升多少？"（你必须自己跑出这个数字）

### 2.8 生成环节
- Prompt 组装：检索片段要有**编号和来源**，要求模型标注引用。
- **拒答机制**：检索结果为空或置信度低时，明确说"知识库中没有"，而不是硬编。

### 2.9 评测（实习生最稀缺的能力）
- **检索指标**：Recall@k（前 k 个里有没有正确答案）、MRR（正确答案排第几）、NDCG、Hit Rate。
- **RAGAS 框架**：faithfulness（答案是否忠于检索内容）、answer relevancy（答非所问程度）、context precision/recall。
- **做法**：自建 20-50 条的评测集（问题+标准答案+相关文档），每次改动跑一遍，看指标变化。**没有评测集的 RAG 项目是空谈**。

### 2.10 Agentic RAG（2026 面试热词）
把 Agent 的"反思"能力接进 RAG：
- **检索前**：查询改写、问题路由（判断要不要检索、检索哪个库）
- **检索中**：多路检索并行、CRAG（检索质量评估，不好就换策略或走联网）
- **检索后**：对答案做一次"是否忠于原文"的校验，不合格就重检索
- **Self-RAG**：模型自己决定"要不要检索、检索结果够不够、要不要重来"
- 这就是小红书那个 up 主说的"RAG 不能太简单"的正确答案。

## 3. Agent 层（W3 主线）

### 3.1 Agent 循环
```
观察 Observation → 思考 Thought → 行动 Action（调工具）→ 观察结果 → ... → 最终答案
```
框架帮你管这个循环（LangChain 的 `create_agent`、LangGraph 的图）。

### 3.2 ReAct 范式
**Re**asoning + **Act**ing：让模型每轮输出"思考过程 + 要执行的动作"，动作执行后把结果追加进上下文再继续。是所有 Agent 框架的祖宗范式。

### 3.3 Planning 规划
- **任务分解**：把"帮我分析这份财报"拆成多个子任务。
- **Plan-and-Execute**：先整体规划再逐步执行（比边想边做更稳，成本更高）。
- **ReWOO**：规划时不调用工具，一次性生成计划，减少 token 消耗。

### 3.4 Memory 记忆（必考）
- **短期记忆**：本次会话的消息列表。问题是会撑爆上下文 → 手段：滑动窗口、对话摘要压缩、token 截断。
- **长期记忆**：跨会话持久化，按 user_id 存储，检索式召回（向量库/KV/关系库）。
- **LangGraph 的 Checkpoint**：把图的状态按 thread_id 持久化，实现"断点续跑"和"多轮会话"。这是 LangGraph 最核心的价值之一。
- **面试**："短期记忆和长期记忆分别怎么实现？上下文超了怎么办？"

### 3.5 Multi-Agent 多智能体
- **Supervisor 模式**：一个主管 agent 分发任务给多个专家 agent（最常见）。
- **Swarm / Handoff**：agent 之间互相转交任务。
- **价值**：复杂任务拆解、角色隔离（避免单个 prompt 过于臃肿）。
- **代价（面试一定要提）**：token 成本成倍上升、延迟变长、调试困难、容易死循环。**能用单 agent 解决就不要上多 agent**——说得出这句话说明你有工程判断力。

### 3.6 Guardrail 护栏与兜底
- 输入侧：敏感词/注入防护（prompt injection）、长度限制。
- 输出侧：格式校验、非法内容过滤。
- 运行侧：工具调用超时、重试次数上限、token 预算上限、最大循环轮数（防止死循环烧钱）。
- **兜底策略**：模型失败时降级到规则/缓存/人工。

### 3.7 Human-in-the-loop 人工介入
Agent 执行到关键/危险动作（如发邮件、下订单、删数据）时暂停，等人确认后再继续。LangGraph 用 `interrupt` 实现。**这是 ToB 场景的刚需**。

## 4. 框架与协议

### 4.1 LangChain
组件库：Model（模型封装）、Prompt Template、**Tool**、Retriever、Chain、Memory。提供统一抽象，换模型只改一行。LCEL 是它的链式表达式语法。

### 4.2 LangGraph（重点）
LangChain 团队的有状态编排框架，把 Agent 建模成**图**：
- **State**：全局状态（一个 dict/typed dict），节点读写它
- **Node**：一个函数（调模型、调工具）
- **Edge**：节点之间的连线；**Conditional Edge** 分支路由（如"检索结果够不够？不够就去改写查询"）
- **Checkpoint**：状态持久化（SQLite/Postgres），支持断点续跑
- **interrupt**：人工介入
- **与 LangChain 的关系**：LangChain 提供零件（模型、工具、检索器），LangGraph 负责**编排和循环**。没有 LangGraph 也能写 Agent，但有循环/分支/持久化的复杂场景会写得很痛苦。

### 4.3 LlamaIndex
偏 RAG/索引方向的框架，数据连接器和索引结构丰富。和 LangChain 有重叠，很多公司混用。

### 4.4 MCP（Model Context Protocol）
- **解决什么问题**：M 个应用 × N 个工具 = M×N 的集成地狱。MCP 把它变成 M+N（大家都对接同一协议）。
- **三个角色**：Host（宿主应用，如 Claude Desktop/你的 Agent）、Client、Server（提供能力的一方）。
- **三种能力**：**Tools**（可执行函数）、**Resources**（可读数据）、**Prompts**（预设提示模板）。
- **传输**：stdio（本地进程）、HTTP/SSE（远程）。
- **面试**："MCP 和 Function Calling 什么关系？"——FC 是模型怎么表达调用意图，MCP 是工具怎么被标准化发现和接入，**不在同一层**。

### 4.5 其他新协议（了解即可，JD 里出现过）
- **A2A**（Agent-to-Agent）：agent 之间对话协作的协议
- **Agent Skills / A2UI**：技能包与 UI 协议
这些是 2026 年的新热点，面试时提一句"我有了解"是加分，但别吹成精通。

### 4.6 官方 SDK
OpenAI Agents SDK、Claude Agent SDK 等。面试时说"我用过 LangGraph，也了解官方 SDK 的设计差异"是加分项。

## 5. 工程化（实习生和学生的分水岭）

### 5.1 后端与流式
- **FastAPI**：写 Agent 服务接口的事实标准（JD 高频词）。
- **SSE / WebSocket**：把 Agent 的中间步骤和最终答案流式推给前端。

### 5.2 异步 asyncio
Agent 要并发调多个工具/多个检索源，`async/await` 能把延迟从相加变成取最大。**JD 里明确写"熟悉异步编程"**。

### 5.3 可观测性
- **LangSmith**（LangChain 官方）、**Langfuse**（开源）：追踪每次调用的完整链路、token 消耗、延迟、失败点。
- 面试："你怎么定位一个 Agent 答错的 case？"——答"靠 trace 回放，看是哪一步检索错了还是生成错了"，这是专业答案。

### 5.4 成本控制
token 预算、结果缓存、模型分级（简单任务用小模型）、批量处理。

### 5.5 部署
Docker 容器化、uv 管理依赖和锁文件、CI 自动跑评测。**你已经在用 uv 了，这就是工程化的一部分**。

## 7. 术语地图速查（一页版）

```
模型层：Token/上下文 · temperature · 幻觉 · CoT · Function Calling · 结构化输出 · 流式
RAG层：解析 → 切分 → Embedding → 向量库 → 混合检索 → Rerank → 生成 → 评测(RAGAS)
Agent层：ReAct 循环 · Planning · Memory(短/长) · Multi-Agent · Guardrail · HITL
框架层：LangChain(零件) · LangGraph(编排) · LlamaIndex · MCP(协议) · A2A
工程层：FastAPI · SSE · asyncio · LangSmith/Langfuse · Docker · uv
```
