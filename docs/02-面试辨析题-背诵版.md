## 通用答题结构（比背答案更重要）

任何一道题，都按这个四段说，长度控制在 40 秒内：

1. **结论**：一句话给出判断（"这两者不在同一层"）
2. **展开**：2-3 个要点，最好用对比或分层（"分输入侧、生成侧、输出侧"）
3. **我项目里怎么做**：落到具体动作（"我实测加了 rerank 之后……"）
4. **边界与代价**：主动说局限（"但它解决不了……"）

**第 3 段和第 4 段是分水岭。** 只答 1、2 段是"看过资料"，答出 3、4 段才是"做过"。

# 第一部分 · 模型与协议（Q1、Q11、Q13、Q15、Q16）

## Q1. Function Calling 和 Tool Calling 的区别？⭐

**结论**：FC 是**模型层能力**，Tool Calling 是**框架层封装**。前者是"模型能不能输出调用意图"，后者是框架帮你把"声明 → 调用 → 回传 → 继续生成"这个循环跑完。

**展开**：

| 维度 | Function Calling | Tool Calling |
|---|---|---|
| 层次 | 模型 API 特性 | 框架封装 |
| 谁提供 | OpenAI / GLM / Qwen 等模型 | LangChain `@tool` + `bind_tools` |
| 输出 | 结构化的调用意图 JSON | 同样从模型拿意图，但执行/回传/再续由框架自动完成 |
| 换模型 | 依赖模型是否支持 | 框架负责抹平不同模型 FC 格式差异 |

**三个关键细节**：
- 模型**永远不执行代码**，执行在你的进程里——这是安全边界，面试常考
- 一次请求可返回多个调用（并行工具调用）
- `tool_choice` 可强制/禁用调用

**口述版**：
> "Function Calling 是模型层的能力——我在请求里声明一批函数的 JSON Schema，模型输出的是'我要调哪个函数、参数是什么'，它自己不执行代码，执行在我的进程里，这是安全边界。Tool Calling 是框架层的封装——LangChain 的 `@tool` 加 `bind_tools` 做的是同一件事，但它自动完成了'调用 → 执行 → 结果回传 → 继续生成'这个循环，还负责抹平不同模型 FC 格式的差异。类比一下：Function Calling 是发动机，Tool Calling 是整车。"

## Q11. MCP 解决什么问题？它和 Function Calling 是一回事吗？⭐

**结论**：不是一回事，也不在同一层。FC 是**模型怎么表达调用意图**（模型层）；MCP 是**工具怎么被标准化发现和接入**（协议层）。两者互补。

**MCP 解决的问题**：M 个应用 × N 个工具 = M×N 的集成地狱 → 变成 M+N。工具方实现一次 server，应用方实现一次 client，就能互通。

**三个角色**：Host（宿主应用）/ Client / Server
**三种能力**：Tools（可执行函数）/ Resources（可读数据）/ Prompts（预设模板）
**两种传输**：stdio（本地进程）/ HTTP + SSE（远程）

**关系**：MCP Server 暴露的工具，最终仍然要通过 Function Calling 机制告诉模型"有哪些可用、参数是什么"。**MCP 管"怎么接进来"，FC 管"模型决定调哪个"。**

**口述版**：
> "不是一回事，它们在不同层。Function Calling 是模型层能力，解决'模型怎么把调用意图表达出来'——你声明 schema，模型输出结构化调用请求。MCP 是协议层，解决'工具怎么被标准化地发现和接入'，它把 M 个应用乘 N 个工具的集成地狱变成 M 加 N——工具方实现一次 server，应用方实现一次 client 就能互通。MCP 有 Host、Client、Server 三个角色，一个 server 提供三类能力：Tools 可执行、Resources 可读数据、Prompts 预设模板；传输上本地用 stdio、远程用 HTTP 加 SSE。两者是互补关系：MCP server 暴露的工具，最终还是要通过 Function Calling 机制让模型知道有哪些可用、参数是什么。"

## Q13. 怎么保证 Agent 输出格式稳定？解析失败怎么兜底？⭐⭐

**结论**：稳定靠**约束生成**（不是靠提示词祈祷），兜底靠**分层降级**。

**稳定手段（从强到弱）**：
1. **结构化输出 / JSON Schema 约束解码**（OpenAI structured outputs；LangChain `with_structured_output` + Pydantic）
2. **Function Calling 反向利用**——把"输出格式"当成一个函数的参数，天然受 schema 约束
3. **JSON Mode**——保证是合法 JSON，但不保证字段齐全
4. **Few-shot 给格式样例** + 明确"只输出 JSON，不要解释"
5. `temperature = 0`

**兜底四层降级**：
1. 解析失败 → 把**解析器报错原文 + 模型原始输出**一起回灌重写（上限 2-3 次）
2. 仍失败 → **宽松解析**：正则抽 JSON 块、去掉 markdown 代码围栏、补全被截断的括号
3. 再失败 → **规则兜底**：默认值 / 上一轮结果 / 降级为关键词抽取
4. 最后 → **显式报错或转人工**，**绝不静默返回错结果**

**最关键的洞察**：重试时必须把**具体错误**告诉模型。只说"格式错了"，模型改不动。

**口述版**：
> "格式稳定我优先用约束生成，而不是靠提示词祈祷：能用 structured output 就用 JSON Schema 约束解码，或者用 Function Calling 反向利用——把输出格式当成一个函数的参数，天然受 schema 限制；退一步用 JSON Mode 加 few-shot 样例，temperature 设零。但工程上一定要假设它会失败，所以我做了四层降级：第一层解析失败时，把解析器的报错原文和模型输出一起回灌让它重写，重试上限两到三次——关键是必须把具体错误告诉它，只说格式错模型改不动；第二层还不行就走宽松解析，正则抽 JSON、去掉代码围栏、补全截断的括号；第三层走规则兜底，返回默认值或上一轮结果；第四层明确报错或者转人工。原则是不能静默返回错误结果，宁可显式失败。"

## Q15. 怎么抑制幻觉？RAG 能完全解决幻觉吗？⭐⭐

**结论**：**不能完全解决**。RAG 只解决"模型不知道"，解决不了"模型知道但不照做"（指令遵循失败），也解决不了"检索到的内容本身就是错的"。

**三种失败模式（主动说出来，非常加分）**：
- 检索未命中 → 模型硬编一个看起来对的答案（**最危险**）
- 检索命中但片段有噪声 → 模型被带偏
- 检索正确、prompt 也清楚 → 模型仍然掺入训练时的先验知识

**三段手段**：
| 位置 | 手段 |
|---|---|
| **输入侧** | 提高检索信噪比（垃圾进垃圾出）、元数据过滤、相关片段放 prompt 头尾 |
| **生成侧** | prompt 约束"只依据参考资料，不足则说未找到"、强制引用编号、temperature 0~0.2、结构化输出 |
| **输出侧** | 答案校验（一次单独的模型调用判断"答案是否被检索内容支持"）、不支持则拒答或重检索 |

**一个容易漏的点**：**很多幻觉的根源是模型没有"说不知道"这个选项**，被迫硬答。所以要显式设计拒答路径。

**口述版**：
> "不能完全解决。RAG 只解决'模型不知道'这一类幻觉，它解决不了'模型知道但没照做'也就是指令遵循失败，也解决不了检索结果本身就是错的或过时的情况。我的思路分三段：输入侧尽量提高检索信噪比，因为垃圾进垃圾出，噪声片段是幻觉最大的来源；生成侧用约束把模型框住，prompt 里明确'只依据参考资料回答，资料不足必须说未找到'，强制标注引用编号，temperature 降到零到零点二；输出侧再做一次校验，用一次单独的模型调用判断'答案是否被检索内容支持'，不支持就拒答或者重检索。另外我会显式设计拒答路径——很多幻觉的根源其实是模型没有'说不知道'这个选项，被迫硬答。"

## Q16. 流式输出在 Agent 场景下有什么额外价值？⭐

**结论**：普通聊天里的流式只是"好看"；Agent 场景下它有三项额外价值。

1. **降低感知延迟**：一轮任务要做多次工具调用，总耗时可能几十秒；最后一次性返回会让用户以为卡死。**总时长不变，体验完全不同。**
2. **可信度与可控性**：把"正在检索知识库""正在执行 SQL"实时展示出来，用户能理解答案怎么来的——**把它当工具而不是黑盒**。ToB 交付尤其重要。
3. **可中断、可纠偏**：看到第一步就走偏，用户能立刻打断补充信息，而不是等 30 秒拿到错答案。**这是人在环最低成本的形态。**

**工程点**：
- 主流是 **SSE**（服务端单向推送），需要双向才上 WebSocket
- **LangGraph 支持 token 级和节点级两种流式事件，节点级就是专门给 Agent 用的**
- 注意：流式会让"输出校验"变难，需要在流结束后再补一次校验

**口述版**：
> "普通聊天里的流式主要是观感，Agent 场景下它有三个额外价值。第一是降低感知延迟——Agent 一次任务要做好几轮工具调用，总耗时可能十几秒甚至几十秒，如果最后一次性返回，用户会以为程序卡死了；把过程流出来，即使总时长没变，体验也完全不同。第二是建立可信度——把'正在检索知识库''正在执行 SQL'这些中间步骤实时展示，用户能看到答案的来源，会把它当成工具而不是黑盒，这在 ToB 交付里尤其重要。第三是可中断、可纠偏——用户看到第一步就走偏了，可以立刻打断补充信息，而不是等三十秒后拿到一个错答案，这是人在环最低成本的一种形态。技术上主流是 SSE，需要双向才上 WebSocket；LangGraph 支持 token 级和节点级两种流式事件，节点级的那个就是专门给 Agent 用的。"

# 第二部分 · RAG（Q4、Q5、Q6、Q7、Q8、Q9、Q14、Q18）

## Q4. RAG 和微调怎么选？什么时候必须微调？⭐⭐

**结论**：**RAG 改的是"知识"（模型知道什么），微调改的是"行为"（模型怎么做事）。** 默认先 RAG——便宜、可随时更新、可溯源。

**为什么不能用微调注入知识**：微调学到的是"像那样说话"的分布，不是"记住那条事实"。用微调灌事实知识，既贵又容易幻觉。

| | RAG | 微调 |
|---|---|---|
| 改什么 | 知识（运行时注入） | 行为 / 风格 / 格式 |
| 更新成本 | 改文档即可 | 重训 + 重新部署 |
| 可溯源 | ✅ 能标注引用 | ❌ 说不清来源 |
| 成本 | 低（推理时多花 token） | 高（训练 + 标注数据） |

**必须微调的五个场景**：
1. 输出格式 / 风格必须高度稳定（固定 JSON、固定话术）
2. 垂直领域术语模型总理解错（医疗、法律、公司黑话）
3. 工具调用可靠性不够，尤其小模型 FC 不稳
4. **降本**：把大模型的复杂 prompt 能力蒸馏到小模型
5. 数据不能出内网且无法做在线检索（边缘 / 离线部署）

**不该微调**："让模型知道我们公司最新政策""知道昨天发生的事"——这些是 RAG。

**口述版**：
> "我用一句话区分：RAG 解决'模型不知道'，微调解决'模型做得不对'。RAG 是运行时把外部知识喂进上下文，所以知识随时可更新、答案可溯源、成本低；微调是改参数，知识固化在权重里，更新一次要重训一次，而且用微调注入事实知识还容易导致幻觉——它学到的是'像那样说话'而不是'记住那条事实'。必须微调的典型场景是：输出格式和风格要求高度稳定、垂直领域术语模型总理解错、要把大模型能力蒸馏到小模型上降本、或者工具调用可靠性不够。工程上常见的组合是 RAG 打底加一次轻量微调调风格，也就是先 RAG 后微调。"

## Q5. 为什么检索要分"召回 + 重排"两阶段？⭐⭐

**结论**：因为两阶段用的是**两种模型结构**，"快"和"准"无法同时满足。

| | 召回 Retrieve | 重排 Rerank |
|---|---|---|
| 结构 | **双塔**（query 和 doc 各自独立编码） | **cross-encoder**（拼在一起过模型） |
| 能否预计算 | ✅ 文档向量可离线算好建索引 | ❌ 每条候选都要现场跑 |
| 速度 | 百万级毫秒返回 | 几十到上百毫秒 / 100 条 |
| 目标 | 宁可多捞，别漏 | 精挑，去伪 |

**量化一下**：100 万文档，双塔只需算一次 query 向量；cross-encoder 要跑 100 万次前向——**算不过来**。所以顺序必然是 粗筛 50-100 → 精排 3-5。

**只有召回会怎样**：top-5 里混入语义相似但答非所问的片段，上下文被污染，模型照样胡说。
**只有精排会怎样**：算不过来。

> **【实测】** 我加 rerank 后 Recall@5 从 ___ 涨到 ___，代价是单次查询多约 ___ ms。（W2 跑完填真实数字）

**口述版**：
> "这两阶段是两种模型结构决定的，不是随意分的。召回阶段是双塔结构，query 和文档各自独立编码成向量，所以文档向量可以离线预计算、建索引，查询时只算 query 一次向量就能在百万级数据里毫秒返回 top-100；精排用的是 cross-encoder，query 和文档拼在一起过模型，能捕捉细粒度交互，准得多，但每条候选都要跑一次前向，全库跑不动。所以工程上必然是先粗筛 50 到 100 条，再精排取 3 到 5 条。我实测过加 rerank 之后的 Recall@5 变化【填实测数字】，代价是单次查询多了大概几十到一百毫秒。"

## Q6. 混合检索为什么比纯向量检索好？怎么融合两路结果？⭐⭐

**结论**：因为两种检索的**失效模式互补**——稠密懂语义但怕精确关键词，稀疏（BM25）精确但怕同义改写。

| | 稠密 Dense | 稀疏 Sparse / BM25 |
|---|---|---|
| 擅长 | 同义改写、语义相近（"怎么退钱" ≈ "退款流程"） | 精确关键词：型号、人名、错误码、缩写 |
| 失手 | 精确关键词不敏感 | 换个说法就搜不到 |

**融合方式：RRF（倒数排名融合）**

```
score(d) = Σ_over_lists 1 / (k + rank_i(d))        # k 通常取 60
```

**RRF 为什么好用**：
- 只看**排名**不看分数 → 完全不用管两路分数量纲不同
- 不用调权重、不用归一化 → 鲁棒
- 比加权求和（要先归一化、权重难调）稳得多

**另一条路**：`bge-m3` 一次前向就能同时输出稠密 + 稀疏表示，所以**不用再单独部署一套 BM25 并对齐索引**——这是选它的理由之一。

**口述版**：
> "因为两种检索的失效模式是互补的：稠密向量检索懂语义、能处理同义改写，但在精确关键词上会飘——型号、人名、错误码、缩写这些反而不敏感；BM25 正好相反，精确匹配强，但问'怎么退钱'搜不到'退款流程'。混合检索两路并行召回，再用 RRF 融合。RRF 的做法是按排名倒数求和，也就是 `1 除以 (k 加 rank)`，k 一般取 60；它的好处是只看排名不看分数，所以完全不用管两路分数量纲不同、也不用调权重，比加权求和稳得多。我用的 bge-m3 一个模型就能同时输出稠密和稀疏表示，所以不用再单独搭一套 BM25 并对齐索引。"

## Q7. chunk 大小怎么定？切大了切小了分别有什么问题？⭐⭐

**结论**：**必须用评测集定，不能拍脑袋。**经验起点：中文 300-800 token，overlap 10%-15%，优先按文档结构切。

| | 症状 |
|---|---|
| **切太大** | 噪声多、不相关内容与答案混在一块；稀释模型注意力；检索精度反而下降（块里只要有半句相关，整体得分就高）；可能超窗 |
| **切太小** | 语义不完整；指代断裂（"该公司"的"该"指谁丢了）；一个完整流程被切成三块，模型只拿到一块就答一半 |

**切分策略优先级**：按文档结构（Markdown 标题层级 / PDF 段落）> 递归字符切分 > 固定长度 > 语义切分（效果最好但最贵）

**进阶：父子块 / small-to-big**
> 用**小 chunk 检索**（精准命中），命中后返回它所属的**大块**（上下文完整）给模型。精度和完整性同时拿到。这是面试加分项。

**口述版**：
> "切大了的问题是噪声多，一个块里只要有半句相关整体得分就高，会把不相关内容和答案混在一起，稀释模型注意力；切小了的问题是语义不完整，指代关系被切断，比如'该公司'的'该'指谁丢了，或者一个完整流程被切碎，模型只拿到一块就答一半。我的做法是中文 300 到 800 token、overlap 百分之十到十五，而且优先按文档自身的结构切——Markdown 按标题层级、PDF 按段落，而不是死按固定长度。另外我用了父子块策略：小 chunk 负责检索命中保证精度，命中后返回它所属的大块给模型保证上下文完整。最终大小是我在评测集上扫过几档之后定的【填实测：扫过哪几档、指标怎么变】。"

## Q8. 向量索引 HNSW 和暴力检索（FLAT）怎么选？⭐

**结论**：FLAT 是暴力计算、**100% 召回**但 O(N)；HNSW 是图索引、**近似召回**但毫秒级。分界线在**数据量**和**延迟要求**。

| | FLAT | HNSW |
|---|---|---|
| 召回 | 100% 精确 | 近似（通常 95-99%） |
| 每次查询 | 全库算一遍，O(N·d) | 沿图跳，近似 O(log N) |
| 建索引 | 无 | 构建慢、吃内存 |
| 适合 | < 10 万条；离线批处理要求精确 | 百万级以上 + 低延迟 |

**HNSW 三个参数**：
| 参数 | 作用 | 何时调 |
|---|---|---|
| `M` | 每层连接数，越大越准越吃内存 | 建索引时 |
| `ef_construction` | 建图时候选池大小，越大图质量越好 | 建索引时 |
| **`ef_search`** | 查询时候选池大小 | **唯一可运行时调的旋钮** |

**实践要点**：`ef_search` 就是"召回率 ↔ 延迟"的那个旋钮——要求准就调大，要求快就调小。**这就是 ANN（近似最近邻）的本质：用一点精度换速度，而且这个 trades-off 可以由你在运行时控制。**

**口述版**：
> "FLAT 就是暴力检索，每个查询都要和全库每个向量算一次相似度，召回率百分之百但复杂度是 O(N)；HNSW 是基于图的近似最近邻，靠分层图跳着找，结果是近似的但毫秒级。选型看两点：数据量和延迟要求。十万条以内、或者离线批处理要求百分百召回，FLAT 就够了；百万级以上还要低延迟，必须上 HNSW。HNSW 有三个关键参数：M 是每个节点的连接数，ef_construction 是建图时的候选池大小，这两个在建索引时定，影响索引质量和内存占用；ef_search 是查询时候选池大小，是唯一可以运行时动态调的旋钮，我一般用它来权衡召回率和延迟——要求准就调大，要求快就调小。用一点精度换速度，而且这个权衡能在运行时控制，这就是 ANN 的本质。"

## Q9. 你的 RAG 项目怎么评测？指标是什么？有没有 bad case 分析？⭐⭐

**结论**：**自建评测集（20-50 条：问题 + 标准答案 + 相关文档 id）→ 分阶段指标 → bad case 分类打标。**

**为什么必须自建评测集**：每个环节都能优化，但没有评测集你就不知道改完是变好还是变差。**「没有评测集的 RAG 项目是空谈」——这句话本身就该说出来。**

**指标分两段（为了能归因）**：

| 阶段 | 指标 | 衡量什么 |
|---|---|---|
| **检索** | Recall@k | 前 k 条里有没有正确答案 |
| | MRR | 正确答案排在第几位 |
| | Hit Rate / NDCG | 命中率 / 排序质量 |
| **生成** | faithfulness | 答案是否被检索内容支持（**最核心**） |
| | answer relevancy | 有没有答非所问 |
| | context precision / recall | 检索进来的内容有多少用、该有的有没有 |

**RAGAS** 就是把这套做成了工具（faithfulness / answer relevancy / context precision / context recall）。

**为什么分两段看**：为了**定位**——Recall@5 低说明问题在检索；召回没问题但 faithfulness 低说明问题在 prompt 或模型。**两者的优化手段完全不同。**

**bad case 四分类（这个分类法本身就是加分项）**：
1. **检索未命中** → 改切分策略、加混合检索
2. **命中但被噪声淹没** → 加 rerank、元数据过滤
3. **检索干净但模型没照做** → 改 prompt、加约束、换模型
4. **问题本身有歧义** → 加查询改写、追问澄清

**口述版**：
> "我建了一个三十条左右的评测集，每条是问题、标准答案、以及对应文档的 id，这样我才能把错误归因到检索还是生成。检索侧看 Recall@k 和 MRR，生成侧用 RAGAS 的 faithfulness 和 answer relevancy。分开看是为了能定位——如果 Recall@5 只有零点六，问题在检索；如果召回没问题但 faithfulness 低，问题在 prompt 或模型，这两类的解法完全不同。bad case 我会打标签分类，主要是四类：检索没命中、命中但被无关片段淹没、检索干净但模型没照做、以及问题本身有歧义。这四类对应的解法不一样——第一类改切分或加混合检索，第二类加 rerank 和元数据过滤，第三类改 prompt 和约束，第四类做查询改写。我觉得有没有评测集是能一眼看出来的，没有评测集的 RAG 项目，改了什么都是凭感觉。"

## Q14. 检索结果不好，你有哪些优化手段？（至少 5 种）⭐⭐

**结论**：别零散列举，**按链路位置分四类说**——这样面试官立刻知道你脑子里有整条链路。

| 位置 | 手段 |
|---|---|
| **索引侧**（改数据） | ① 切分策略优化（语义切分 / 按结构切 / 父子块）<br>② 换 embedding 模型或做领域微调<br>③ 把标题、摘要、关键词写进 metadata<br>④ 建同义词表 / 术语词典，查询时扩展 |
| **召回侧**（改检索） | ⑤ 混合检索（稠密 + 稀疏 + RRF）<br>⑥ 多路召回：multi-query 生成多个改写分别召回再融合<br>⑦ 元数据过滤：先缩小范围再算向量<br>⑧ 调参：top-k、ef_search |
| **排序侧**（改排序） | ⑨ 加 cross-encoder rerank<br>⑩ MMR 去重，避免 top-5 全是同一段<br>⑪ 业务信号重排（时间衰减、权威性、点击率） |
| **查询侧**（改问题） | ⑫ 查询改写：多轮指代消解、口语转书面<br>⑬ HyDE：先生成假设答案再检索<br>⑭ 问题拆解 / multi-hop |
| **生成侧**（改用法） | ⑮ 上下文压缩，只保留相关句<br>⑯ 强制引用 + 拒答 |

**口述版**（挑 5-6 个说透，不要全念）：
> "我会按链路位置分四类说。索引侧：切分策略是最影响上限的，我优先按文档结构切并做父子块，另外给每个 chunk 补标题和摘要这类元数据，检索质量提升明显。召回侧：加混合检索，稠密加 BM25 用 RRF 融合；再做 multi-query 多路召回，同一个问题生成几个改写分别召回再融合；还有元数据过滤，先在时间或来源上缩小范围再算向量。排序侧：加 cross-encoder rerank，以及用 MMR 去重，避免 top-5 全是同一段内容。查询侧：做查询改写，多轮对话里先做指代消解把'它'还原成具体名词，短问题用 HyDE 先生成一段假设答案再拿它去检索。生成侧：把长片段压成只含相关句，再强制引用和拒答。这四类里我实测收益最大的是 rerank 和切分策略【填实测数字】。"

## Q18. 为什么要做查询改写？HyDE 是什么？⭐

**结论**：因为**用户的问法和文档的写法天然不对齐**——用户问得短、口语、带指代，文档是书面语、长句、术语化。

**改写要解决的四个具体问题（按重要性）**：
1. **多轮指代消解**（**最关键，多轮对话必做**）："它多少钱？" → "iPhone 17 Pro 多少钱？"——不还原的话，"它"这个 token 在向量里几乎无信息
2. **口语 → 书面语**："怎么退钱" → "退款流程、申请条件"
3. **太短、缺关键词**：补全隐含前提
4. **一个问题其实含多个子问题** → 拆成多个 query 分别检索（multi-query / multi-hop）

**HyDE（Hypothetical Document Embeddings）**：
- **做法**：让 LLM 针对问题**先编一段假设性答案**，用这段答案的向量去检索
- **为什么有效**：答案和文档在语义空间里更接近，而问题和文档的表述差异大。相当于把"**问题 → 文档**"的跨域匹配，变成"**文档 → 文档**"的同域匹配
- **代价**：多一次 LLM 调用；假设答案可能把方向带偏（引入幻觉到检索里）
- **所以**：作为**多路召回中的一路**，而不是唯一路径
- **适合**：问题短、领域术语多、没有查询日志可用的场景

**口述版**：
> "做查询改写是因为用户的问法和文档的写法天然不对齐——用户问得短、口语、带指代，文档是书面语和术语。最必须做的是多轮对话的指代消解，比如用户上一轮问 iPhone 17 的价格，这轮问'它多少钱'，直接拿'它多少钱'去检索，'它'在向量里完全没信息，必须还原成具体名词。其次是口语到书面语的转换，'怎么退钱'要改写成'退款流程、申请条件'这类文档里的说法。还有把包含多个子问题的问题拆成多个 query 分别检索再融合，这就是 multi-query。HyDE 是另一种思路：不直接检索问题，而是先让模型针对问题编一段假设性答案，用这段答案的向量去检索。原理是答案和文档在语义空间里更接近，相当于把'问题到文档'的跨域匹配变成了'文档到文档'的同域匹配，所以效果更好。代价是多一次 LLM 调用，假设答案也可能把方向带偏，所以我会把它作为多路召回里的一路，而不是唯一路径。"

## Q2. LangChain 和 LangGraph 分别解决什么问题？能不用 LangGraph 写 Agent 吗？⭐⭐

**结论**：LangChain 提供**零件 + 统一抽象**（模型、提示、工具、检索器），LangGraph 提供**执行引擎**（状态、节点、边、持久化、中断）。**能不用**——Agent 的本质就是 `while` 循环加 messages，十几行就写得出来；但一旦要持久化、分支、HITL、自定义拓扑，自己实现等于重写 LangGraph。

**2026 现状（必须知道，这是很多人答错的点）**：
- LangChain 1.0 与 LangGraph 1.0 于 2025-10-22 同时 GA
- 此后 **LangGraph 是 runtime，LangChain 是它上面的高层 API**——`create_agent` 内部返回的就是一个 LangGraph 图
- **`AgentExecutor` 已弃用**；`langchain-community` 已归档
- **LCEL 没被弃用**，但定位从"默认写法"变成"固定线性流水线的表达方式"（因为 LCEL 是 DAG，表达不了循环）

**不用 LangGraph 的方案**：手写 ReAct 循环 / OpenAI Agents SDK / CrewAI / AutoGen

**只有 LangGraph 才有的**：checkpointer 断点续跑、`interrupt` HITL、条件边路由、子图、并行 fan-out、时间旅行调试

**口述版**：
> "LangChain 是零件库加统一抽象——模型、提示、工具、检索器都实现同一套接口，换模型只改一行，它的组合算子就是 LCEL。LangGraph 是执行引擎，把 Agent 建模成图：State 是显式状态、Node 是函数、Edge 负责连线和条件路由，再加 checkpointer 做持久化。能不能不用 LangGraph？能——Agent 的本质就是 while 循环加一个 messages 列表，十二行就能写出来。但一旦你要断点续跑、要人工审批中断、要在执行中途查看和修改状态，自己实现就等于重写 LangGraph。1.0 之后这两个已经分层了：LangGraph 是 runtime，LangChain 是它上面的高层 API，create_agent 返回的就是一个 LangGraph 图——所以现在不是二选一，而是默认用 create_agent，需要自定义拓扑时再下探到 StateGraph。"

## Q3. 短期记忆和长期记忆怎么实现？上下文超限怎么办？⭐⭐

**结论**：短期 = 本次会话的 `messages` 列表（问题是**单调增长**）；长期 = 跨会话按 `user_id` 持久化 + 检索式召回（难点是**什么时候该想起来**）。

**先纠正一个常见混淆**：**LangGraph 的 checkpointer 解决的是"断点续跑 / 多轮会话"，不是"上下文压缩"。** 这两件事很多人混着说。

**短期压缩三手段**：
| 手段 | 做法 | 代价 |
|---|---|---|
| 滑动窗口 | 只保留最近 N 轮 | 丢早期信息 |
| 摘要压缩 | 用 LLM 把更早的历史压成一段 | 一次额外调用，且不可逆 |
| 结构化记忆 | 把稳定事实抽成字段，不留原文 | 需要设计 schema |

**长期存储三种载体**：向量库（语义召回）/ KV（事实型，如"偏好中文"）/ 关系库（约束型，如权限）

**上下文超限的完整回答分三层**：
1. **进窗口前**：压缩（摘要 / 抽取）+ 检索式注入（只放相关记忆，不要全灌）
2. **窗口内**：滑动窗口 + **重要信息放头尾**（lost-in-the-middle 现象）
3. **工程**：Prompt Caching 让重复前缀不重复计费；换更大窗口的模型是最后手段（贵，且中间照样遗忘）

**口述版**：
> "短期记忆就是本次会话的 messages 列表，按轮追加。它的核心问题不是'存不下'，而是每轮都要把全量历史重新传给模型，所以成本随轮数累积增长——这也是 Agent 成本曲线陡的原因。压缩我一般做三层：滑动窗口保留最近 N 轮、对更早的历史做 LLM 摘要压缩、把稳定事实抽成结构化字段而不是保留原文。长期记忆是跨会话的，按 user_id 持久化，用向量库做语义召回，或者 KV 存事实型偏好；难点不在存，而在于'什么时候该想起来'，所以我一般显式做一层记忆检索再注入，而不是全灌。另外要区分一下，LangGraph 的 checkpointer 解决的是断点续跑和多轮会话，它和上下文压缩是两件事。"

## Q10. Agent 死循环了怎么办？成本失控了怎么办？⭐⭐

**结论**：死循环**先分成因再定解**（靠 trace）；成本控制必须由**框架层强制**，不能指望模型自己停。

**第一步：从 trace 判断是哪类问题**

| 现象 | 成因 | 解法 |
|---|---|---|
| 反复用同样参数调同一个工具、拿到同样结果 | **循环卡死** | 框架层做**重复动作检测**：对 tool_call 做签名 hash，连续重复 N 次强制跳出 |
| 每轮换工具但离目标越来越远 | **规划失败** | 上 Plan-and-Execute，或换更强模型 |
| 一直是工具报错 | 不是循环问题 | 工具或 schema 设计有问题，回去改工具 |

**第二步：硬约束（绝不能指望模型自己停）**
1. `max_iterations` / `recursion_limit` —— 最大轮数
2. **累计 token 预算** —— 超阈值直接终止
3. 单次工具超时 + 整体 wall-clock 超时

**成本控制的四层（在上面三道闸之上）**
4. **结果缓存**：相同输入返回缓存
5. **模型分级**：规划用大模型，执行用小模型
6. **Prompt Caching**：重复前缀不重复计费
7. **按会话统计 token 用量 + 异常告警**（没有观测就没有控制）

**口述版**：
> "死循环我分两步看。第一步从 trace 判断成因：如果它反复用同样参数调同一个工具、拿到同样结果，那是循环卡死，解法是在框架层做重复动作检测——对工具调用做签名 hash，连续重复就强制跳出；如果它每轮都在换工具但离目标越来越远，那是规划失败，要靠 Plan-and-Execute 或者换更强的模型；如果一直是工具报错，那根本不是循环问题，是工具或 schema 没设计好。第二步是工程上的硬约束，这部分绝不能指望模型自己停：设最大轮数上限、设累计 token 预算、设单次工具超时和整体 wall-clock 超时，这三个是必须的。成本上我还有四层：相同输入走结果缓存、规划和执行做模型分级、开 prompt caching 让重复前缀不重复计费、再按会话统计 token 用量做告警。没有观测就没有控制。"

## Q12. 什么场景下不该用 Multi-Agent？⭐⭐

**结论**：**能用单 Agent 加工具解决，就不要上多 Agent。** 该问的不是"能不能拆"，而是"拆开的收益能不能覆盖通信开销"。

**四种不该用的场景**：
1. **上下文总量小**：一个 prompt 装得下 → 拆开只是徒增通信损耗
2. **子任务强串行**：B 完全依赖 A 的输出 → 拆开等于把函数调用换成对话，只增加出错面
3. **延迟敏感**：每多一层 agent 就多至少一次模型往返
4. **需要全局一致性**：多个 agent 分头写同一份东西（写文档、改代码），最后很难收敛

**Multi-Agent 的真实代价（一定要主动说）**：
- token 成本成倍上涨（每个 agent 都有 system prompt 和自己的上下文）
- 延迟变长
- **错误跨 agent 传播放大**（上游错一点，下游放大一圈）
- **debug 困难**：trace 从链变成网
- 职责边界难划清，容易出现"都以为对方做了"

**什么时候值得上**：
- 子任务**上下文能完全隔离**（如并行处理 20 份财报各出摘要）
- 需要**不同工具集 / 权限**（安全隔离）
- 需要**不同角色方法论**（研究员 vs 审稿人）+ 互相校验
- 上下文确实塞不下，必须并行分片

**口述版**：
> "我的原则是能用单 Agent 加工具解决就不上多 Agent，因为代价是实打实的：token 成倍上涨、延迟变长、错误会在 agent 之间传播放大、trace 从链变成网导致很难 debug，而且职责边界很难划干净。具体不该用的有四类：一是上下文总量小、一个 prompt 装得下，拆开只是徒增通信损耗；二是子任务强串行，B 完全依赖 A 的输出，那拆开相当于把普通函数调用换成对话，只增加了出错面；三是延迟敏感的在线场景，每多一层就多至少一次模型往返；四是需要全局一致性的任务，比如多个 agent 分头写一份文档，最后很难收敛。真正值得上的是子任务上下文能完全隔离的场景，比如并行处理二十份财报各出摘要；或者需要不同权限、不同角色互相校验的场景。"

## Q17. 工具调用超时/失败，你的兜底策略是什么？⭐⭐

**结论**：先分**读 / 写**，再分**可重试 / 不可重试**。读操作自动重试，写操作**必须先保幂等**再谈重试。

**七层策略（从上到下）**：
1. **超时**：每个工具**单独设**超时（不是一个全局值）；长任务改异步 + 轮询
2. **重试**：只重试**幂等的读操作**；指数退避 + 抖动；上限 2-3 次
3. **降级**：主工具失败换备选——主检索挂了走缓存 / 备用索引；联网失败退回本地知识库
4. **回灌**：把**结构化错误信息**返回给模型，让它换策略（换参数、换工具、放弃这个子目标）
5. **幂等**：写操作带幂等键（`request_id`），否则重试会造成重复下单、重复发邮件
6. **熔断**：同一工具连续失败 N 次直接短路，不再消耗 token 和延迟
7. **人工接管**：关键路径失败直接转人工，不硬撑

**第 4 点是 Agent 相对固定 workflow 的核心优势**——workflow 遇工具失败只能报错，Agent 可以自己换路。

**口述版**：
> "我先把工具分成读操作和写操作，两类策略不一样。读操作可以安全重试，我用指数退避加重试上限两到三次，超时是每个工具单独设的，不用全局一个值。写操作不能盲目重试，必须先保证幂等——请求带幂等键，否则重试会造成重复下单、重复发邮件。重试还不行就降级：主检索失败走缓存或备用索引，联网失败退回本地知识库。然后关键的一步是把结构化错误信息回灌给模型，让它自己换策略——换参数、换工具或者放弃这个子目标，这是 Agent 相比固定 workflow 最核心的优势，workflow 遇到工具失败只能报错退出。再往上是熔断，同一个工具连续失败若干次就短路，不再无谓消耗延迟和 token。最后如果关键路径确实走不通，我倾向于直接转人工而不是硬撑——ToB 场景里，一次错误的成功比一次明确的失败代价大得多。"

## Q20. Human-in-the-loop 怎么实现？什么业务场景必须要？⭐⭐

**结论**：LangGraph 的 `interrupt()`——把状态快照存进 checkpointer 后**直接返回调用方，不阻塞进程**；靠 `thread_id` 恢复。

**三个必需条件**：checkpointer（必须**持久化**，生产用 Sqlite/Postgres）、`thread_id`、payload 可 JSON 序列化

**⚠ 最大的坑：恢复时节点会从函数开头重跑**，不是从 `interrupt()` 那行继续。
→ 所以 **`interrupt()` 之前只做只读的状态收集，所有副作用放它后面**，否则会重复发邮件、重复执行 SQL。

**产品取舍**：**只在检测到危险动作时中断，不是每步都停。** 审批太密集用户会直接关掉审批，安全机制反而失效。

**必须上的五类场景**：
1. **写操作**：发邮件、下单、转账、删改数据库、提交工单
2. **高代价不可逆**：生产环境变更、对外发布
3. **合规要求**：金融 / 医疗 / 政务必须有审批留痕——**责任必须落在人身上**
4. **低置信度**：模型自己判断不确定，转人工
5. **权限边界**：越权操作即使模型想做也必须拦截

**口述版**：
> "HITL 我用 LangGraph 的 interrupt 实现。它的机制是把当前状态快照存进 checkpointer，然后把控制权返回给调用方，不阻塞进程也不 sleep，所以审批可以跨小时甚至跨服务重启，靠 thread_id 恢复；三个必需条件是持久化 checkpointer、thread_id、以及 interrupt 的 payload 必须能 JSON 序列化。有一个坑必须注意：恢复时节点是从函数开头重跑的，不是从 interrupt 那一行继续，所以 interrupt 之前的代码我会保证只做只读的状态收集，所有副作用都放在它之后，否则会重复发邮件、重复执行 SQL。另外我只在检测到破坏性操作时中断，不是每步都停——审批太密集用户会直接关掉审批，安全机制反而失效。必须上的场景主要是写操作，比如发邮件、下单、转账、改数据库；还有合规必须留痕的金融医疗政务场景，因为责任必须落在人身上；以及模型自己置信度低的时候转人工。"

# 第四部分 · 工程与成本（Q19）

## Q19. 你项目里 token 成本怎么优化的？（Text2SQL 有现成答案）⭐⭐

**结论**：Text2SQL 的成本大头**不是用户问题，而是 schema 和 few-shot 示例**。所以优化全从这里下手。

**七条做法（按收益排序）**：

| # | 做法 | 说明 |
|---|---|---|
| 1 | **Schema 裁剪** | 不要塞全库表结构。先用向量检索/规则选出**相关表**，只注入这几张表的 DDL + 字段注释。**通常能砍掉 70%+ 输入 token**，而且顺带提升准确率（减少干扰） |
| 2 | **Few-shot 动态选取** | 不固定塞 10 个示例。从示例库里用向量检索选**最相似的 2-3 条**（few-shot 检索器） |
| 3 | **结果缓存** | 问题归一化后做 key，相同/相近查询直接返回缓存 |
| 4 | **模型分级** | 生成 SQL 用便宜模型；只在**执行报错需要纠错**时升级到强模型 |
| 5 | **本地校验前置** | 先用 `sqlglot` / `EXPLAIN` 做语法与 schema 校验，本地能发现的错别浪费一次模型调用 |
| 6 | **限制重试 + 错误精简** | 纠错循环上限 3 次；回灌报错时只传**关键几行**，不要整段堆栈 |
| 7 | **Prompt Caching** | 把 system prompt + schema 作为**稳定前缀**开缓存。⚠ 前缀必须字节级一致 → **动态内容一律放后面**，否则前缀一变缓存全失效 |

**⚠ 这一题必须带数字说**：比如"schema 裁剪把输入从 ___ token 压到 ___ token"。W3 做完补上。

**口述版**：
> "这个项目里 token 的大头不是用户问题，而是 schema 和 few-shot 示例，所以优化都从这两处下手。第一是 schema 裁剪，不要把整个库的表结构全塞进 prompt，我先用向量检索或规则把问题相关的表选出来，只注入这几张表的 DDL 和字段注释，这一步就能砍掉七成以上的输入 token——这也是收益最大的一步，因为同时减少了干扰、提升了准确率。第二是 few-shot 动态选取，固定塞十个示例既贵又没用，我改成用向量检索选最相似的二到三条。第三是结果缓存，把问题归一化后做 key。第四是模型分级，生成 SQL 用便宜模型，只有执行报错需要纠错时才升级到强模型。第五是本地校验前置，先用 SQL 解析库做语法和 schema 校验，本地能发现的错就不浪费一次模型调用。第六是纠错循环限三次，回灌报错时只回传关键几行而不是整个堆栈。最后是 prompt caching，把 system prompt 和 schema 作为稳定前缀开缓存，注意动态内容一律放后面，否则前缀一变缓存全失效。"
